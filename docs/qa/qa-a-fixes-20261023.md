## ZIP transport investigation

The audit’s `native-download-history.txt` records Safari receiving `http://127.0.0.1:5630/python-practice.zip`, expecting 158 bytes, loading zero, then finishing about 61 seconds later. This is a local fixture/system-browser transport boundary, not evidence of a client file-write race. `mobile/src/components/course-file-card.tsx` awaits `downloadCurriculumResource`, validates the returned URL and awaits `Linking.openURL`; it neither allocates a file nor writes bytes nor displays a completed-download claim. The strengthened deferred-response test proves no browser handoff occurs before signing finishes and concurrent taps cannot start a second preparation.

The same original 158-byte archive passes `unzip -t`. Web requires an HTTPS signed URL, so browser transport uses an intercepted synthetic HTTPS URL with those exact bytes; using a loopback HTTP URL is intentionally rejected by the web helper. No production storage credentials are used. The finding is classified as a test fixture/system-browser transport limitation with **no demonstrated client implementation bug**. A real HTTPS ZIP download on native Safari/device remains **not_run** under the no-simulator constraint; this is not a production-download certification.
